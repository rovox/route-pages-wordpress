# AGENTS.md

WordPress plugin (Trufi Route Pages) with **no build tooling**: no composer, no autoloader, no tests, no linter, no CI. CONTRIBUTING.md mentions "test suite"/"lint check", but no such tooling exists in this repo. All changes are verified in a real WordPress install against a Trufi GraphQL endpoint: hit `/wp-sitemap-routes-1.xml` for the sitemap, `/{base}` for the routes index page, or a rendered route page at `/{base}/<name>/<route-code>`.

Working-tree note: `trufi-website-modules/` is a **separate, untracked git repo** (a local Docker dev stack: wordpress/mysql/phpmyadmin). It is unrelated to the plugin — don't edit, inspect, or commit it. The plugin repo has its own tracked dev stack instead: `docker-compose.dev.yml` (see README.md). It isn't named `docker-compose.yml` because `.gitignore` excludes that exact filename and any `docker`/`.docker` path — a rule already in this repo, kept for ad-hoc local files.

## Bootstrap & adding new code

- Entry point is `trufi-maps.php` (the plugin file). It `require`s every PHP file **in a fixed order**; namespaced classes (`App\...`) are NOT autoloaded.
- New classes/files must be added to the require chain in `trufi-maps.php`, or required at point of use (see `functions/sitemap-provider.php:7`).
- The main file refuses to load below `Requires PHP: 8.1` (guarded by `version_compare`). Code may use typed properties and union types.
- Admin-only files are loaded only when `is_admin()`.

## How route pages work (virtual posts)

- Requests match rewrite rule `^{base}/([^/]+)/([^/]+)/?` in `functions/rewrite-rules.php`, mapping to query vars `trufi_map_name` + `trufi_map_id`.
- No real post exists. `functions/template-redirect.php` (on `template_redirect`) fabricates a global `$post`, stamps `is_page`/`is_singular` on `$wp_query`, and injects minified template HTML into `$post->post_content`. `the_title` is filtered to the route name.
- `{base}` defaults to `routes` but is derived from the "Base Page for Maps" setting via the shared `trufi_get_base_path()` helper (`functions/functions.php`), used by both the rewrite rule and the sitemap provider — keep any future URL-generation code going through that helper rather than re-deriving the base path, or it'll drift again (it used to: the sitemap called `get_page_uri()` while the rewrite rule called `get_post_field('post_name', ...)`, diverging for non-top-level base pages).
- Route URL slug = `sanitize_title(`longName with `→` replaced by a locale word`)` — see `App/Utility.php::replaceArrowWithWord`. `trufi_pattern_url()` (`functions.php`) reimplements this same scheme so the index page's per-route share button can link straight to a route detail page without a fetch; keep it in sync with `TrufiRoutesSitemapProvider::getRouteUrls()` if the slug scheme ever changes (verified to produce byte-identical URLs to the sitemap for the same pattern).
- The base page itself (`GET /{base}`, i.e. the page set as "Base Page for Maps", no route segments) renders a **routes index**: searchable sidebar + map of all lines via `trufi_maps_render_routes_index()` (`functions/template-redirect.php`) + `templates/routes-index-template.html`. It calls `remove_all_filters('the_content')` before injecting; WP's default content filters (wpautop, shortcodes, emoji…) corrupt the embedded JS — keep bypassing them if you touch that function. The virtual route page (`templates/map-template.html`, injected by the same file's route branch) does the same for the same reason: its inline script passes HTML strings (e.g. Leaflet `divIcon`s) that wpautop would mangle.
- The REST endpoint and the page both `rawurldecode` the pattern id captured from the URL segment: the index JS sends it `encodeURIComponent`-encoded (`:` → `%3A`) and WP doesn't decode path segments, so an undecoded id 404s.
- The index fetches per-pattern geometry+stops on demand from `GET /wp-json/trufi/v1/pattern/{id}` (`functions/rest-api.php`), which shares the same `trufi_route_data_{mapId}` transient as the virtual route page and `enqueue-scripts.php`'s asset-loading fetch (so all three stay in sync and are cleared together by the cache cleanup).
- Data access (both pages + the REST endpoint) goes through `trufi_fetch_route_data($mapId)` / `trufi_fetch_index_data()` in `functions/functions.php` — thin wrappers around `TrufiApi` that do the "check transient, else fetch + cache" dance once instead of it being duplicated per call site. Add any new API call the same way rather than re-inlining the transient check.
- `App\Api\TrufiApi::fetchRoute()`'s GraphQL query includes `stops { name, lat, lon, code }` on top of `route`/`geometry`. `Stop.name` in this feed *is* the street/intersection name (e.g. "Avenida Río Paraguay", or literally "Innominada" when the feed has none) — that's the source for the route detail page's "Paradas" list and the street-name marker tooltips, not a separate field. Don't drop `stops` from the query without checking both call sites (route detail page's stop list, REST endpoint's response) still work without it.
- **There is no real "sindicato"/operator data.** `route.agency.name` reports the literal string `"default"` for every single pattern on the configured endpoint (verified against all patterns) — GTFS agency data just isn't populated in this feed. `trufi_group_patterns_by_line()` groups by route `shortName` instead; don't build UI that assumes a real per-operator grouping exists unless a different data source is wired in.

## Templates & rendering

- `templates/map-template.html` and `templates/routes-index-template.html` are now **plain static HTML shells** with only text-content `{{placeholder}}` tokens (headline, stats, image/URL attributes — all in ordinary HTML text/attribute positions). There is no inline `<style>`/`<script>` in either file anymore, and no token is spliced into raw CSS/JS syntax positions. This was a deliberate change from the old "splice raw JSON into an inline `<script>` block" approach: besides being a code-editor false-positive magnet (`{{token}}` isn't valid CSS/JS on its own), embedding `json_encode($routeData)` unescaped inside a `<script>` block was a real `</script>`-breakout XSS vector for any route/stop name containing that sequence — GTFS data comes from an external API we don't control. All structured data now travels through `wp_localize_script` (see below), which is run through `trufi_defang_script_close()` first as defense in depth.
- CSS/JS for both pages lives in `assets/css/` and `assets/js/`, loaded via `functions/enqueue-scripts.php` (hooked on `wp_enqueue_scripts`, gated to the two page types this plugin renders) — see "Frontend assets" below. Leaflet 1.7.1 itself stays a raw `<script src>`/`<link>` from unpkg, echoed by `trufi_add_header_tags()` (`functions/functions.php`, on `wp_head` priority 7) rather than a WP-enqueued asset — it isn't re-registered as a WP dependency (that would load it twice); ordering is guaranteed because it prints in `wp_head` before any of our footer-loaded module scripts run.
- Both maps create maps with `zoomControl: false` and re-add the zoom at `bottomright`, restyle `.leaflet-control-zoom` (dark/pink theme) via the shared `.trufi-map` class, and cap `.leaflet-top/.leaflet-bottom` z-index at 400 while the map container gets `z-index: 0; isolation: isolate`. This is load-bearing: the OnePress header is `z-index: 1000`, and without isolation the Leaflet controls (also 1000) escape the map and stack above the sticky header. If you move these styles, keep the isolation.
- The index keeps its search UI as `.trufi-searchbar` floating over the map top (desktop) and a bottom-center `.trufi-map-hint` pill. `.trufi-index-body` (sidebar+map row) gets a generous **bounded** height (`80vh`, capped at `860px`) rather than the page itself being height-locked. **Don't go back to `height: calc(100dvh - 82px)` on `.trufi-index`/the whole page** — that was tried and reverted: the theme's `#primary` padding (40px top+bottom) plus the footer mean the page is always taller than one viewport regardless, so it never actually achieved "no scroll"; it just made the `dvh` unit recalculate against a page that scrolls anyway, which read as the footer jumping/"sticky" during scroll on mobile (browser chrome show/hide changes `dvh`). Bounding just the sidebar+map row avoids that. The route detail page (`assets/css/trufi-route.css`) uses the same bounded-height pattern (`.trufi-route-body`/`.trufi-route-map-wrap` at `70vh`) and never had this problem. **On mobile (`<=780px`, `assets/css/trufi-index.css`)** the index becomes a normal stacked scrolling page: `.trufi-index-body` switches to an auto-height column flex layout, the searchbar un-floats into a static card, the map gets a fixed ~320px height, and `order` flips the visual order to hero → search/map → routes list (DOM order is left unchanged: list, then map-wrap). The route detail page follows the same map-first mobile stacking pattern.
- Route markers follow one convention everywhere (`Trufi.routeDraw.drawEndpoints`, `assets/js/trufi-route-draw.js`): **origin = small solid green dot, destination = red map-pin icon** (`Trufi.icons.pinMarkerSvg()`, a filled teardrop+white-dot SVG rendered via an `L.divIcon` — not a `circleMarker`, and its wrapper needs `.trufi-pin-wrap { background: transparent; border: none; }` in `trufi-shared.css` or Leaflet's default `.leaflet-div-icon` box/border shows through). Intermediate stops stay small gray dots (`drawStops`). The polyline + direction arrows use the admin-configurable `trufi_line_color` option (currently cyan, `#00BCD4`) — that option is the single source of truth for the route's drawn color; don't hardcode a different color for it in CSS/JS.
- Both maps have a geolocation "Mi ubicación" button (browser Geolocation API + `map.locate`, needs HTTPS on production; draws a pulsing marker + accuracy circle), implemented once in `assets/js/trufi-geo.js` (`Trufi.geo.attach(map, {button, onHint})`) and used by both `trufi-index.js` and `trufi-route.js` — don't re-duplicate this block if you touch it, fix it in the shared module. It can be turned off from the plugin Settings: the `trufi_show_location` option drives a `data-show-location="1"/"0"` attribute on the button (CSS hides it on `"0"`, see `trufi-shared.css`), and `Trufi.geo.attach` no-ops its button wiring when the element is missing. On GPS failure/absence it falls back to an approximate IP-based location via client-side `fetch('https://ipwho.is/')` (free, CORS `*`, no key; city/ISP-level precision, drawn as a ~3 km dashed circle + "Ubicación aproximada por IP" hint). Note: in the dev stack the IP lookup resolves the machine's egress IP (a datacenter), not the browser's local network — a false reading in local test.
- The active theme (OnePress) renders its own `<h1 class="entry-title">` page-title banner (wrapped in `.page-header`) above `the_content` on every page, including both of this plugin's virtual pages — there's no filter to suppress just this from the plugin side without a child theme, so `trufi-shared.css` just hides `.page-header` outright. That rule only ever loads on these two page types (gated by `enqueue-scripts.php`), so it's effectively scoped despite `.page-header` being theme markup, not ours.

## Frontend assets (CSS/JS modules)

`functions/enqueue-scripts.php` is the single place that decides which of the two page types is being rendered (checking the same query vars as `template_redirect.php`, since the two hooks don't share state) and enqueues accordingly. All page data (GraphQL results, option values, REST URL, map center/zoom, etc.) is handed to the page's bootstrap script via `wp_localize_script` as `trufiIndexConfig` / `trufiRouteConfig` — don't add new `{{placeholder}}` tokens for anything JS needs; extend the localized config object instead.

- `assets/css/trufi-shared.css` — design tokens (`:root` vars), hero banner, stat blocks, list-title header, line badge, buttons, geo button/pulse marker, stop-list dots, Leaflet chrome theming, `.page-header` hide. Loaded on both pages.
- `assets/css/trufi-index.css` / `assets/css/trufi-route.css` — page-specific layout (including each page's mobile breakpoint), building on the shared classes above.
- `assets/js/trufi-icons.js` — small lucide-style inline SVG icon set (`Trufi.icons`); auto-mounts into any `<span data-icon="name">` on `DOMContentLoaded`, and exposes `Trufi.icons.mount(root)` for icons added dynamically afterward (e.g. list rows built by `trufi-index.js`).
- `assets/js/trufi-geo.js` — the shared "Mi ubicación" button module (`Trufi.geo.attach`), described above.
- `assets/js/trufi-distance.js` — haversine distance helpers (`Trufi.distance`); the route detail page's headline distance stat is computed server-side instead (`trufi_route_distance_km()` in `functions.php`, so it works with JS disabled) — this module is for client-side use, e.g. a future index-page preview.
- `assets/js/trufi-share.js` — `Trufi.share.copyOrShare(url, title, btnEl)`: Web Share API on mobile, clipboard-copy + a brief `.is-copied` acknowledgement on `btnEl` otherwise. Used by the route detail page's share button and by each route row's share icon in the index sidebar (which shares `pattern.url` — see below).
- `assets/js/trufi-route-draw.js` — draws a pattern on a Leaflet map: polyline, direction arrows, green-dot origin / red-pin destination markers, and one small marker per stop with a tooltip showing its street name (`Trufi.routeDraw.drawPattern`). Shared by the index page's on-demand preview and the route detail page's main map — this is the module to touch for anything about how a route is painted.
- `assets/js/trufi-api.js` — fetch wrapper (with an in-memory cache) around the REST pattern endpoint, used by the index page when a route is selected.
- `assets/js/trufi-search.js` — pure `Trufi.search.filterLines(lines, {query, mode})`, kept separate from DOM/rendering code in `trufi-index.js`.
- `assets/js/trufi-index.js` / `assets/js/trufi-route.js` — each page's bootstrap: reads its localized config, builds the map, and wires the above modules together. Keep page-specific DOM/rendering code here; put anything reusable in one of the modules above instead. Each pattern in `trufiIndexConfig.lines[].patterns[]` carries a server-computed `url` field (`trufi_pattern_url()`) - that's what the index list's per-row share button links to, not something built client-side.

## Caching & settings

- Three transient caches exist (all keep the `trufi_route%` prefix so the cache cleanup catches them):
  - Per-route: `trufi_route_data_{mapId}`, read via `trufi_fetch_route_data()` (`functions.php`, used by `template-redirect.php`, `rest-api.php`, and `enqueue-scripts.php`)
  - Routes index list: `trufi_routes_index_list`, read via `trufi_fetch_index_data()` (same file, used by `template-redirect.php` and `enqueue-scripts.php`)
  - Sitemap: `trufi_routes_sitemap_xml` in the sitemap provider
- TTL comes from the `trufi_cache_ttl` option (hours). The admin "Clear Cache" page (`delete_trufi_transients()` in admin/transient-cache-clear.php) clears via raw `option_name LIKE` SQL and only catches the `trufi_route%` prefix — any newly named transient must keep that prefix or be added to the query.
- All option names are `TRUFI_*_OPTION` constants centralized in `functions/constants.php` — reuse, don't string-literal option names.
- Saving settings flushes rewrite rules and clears transients (`admin/admin-settings.php:62-63`).

## Conventions

- Text domain is inconsistent: `TrufiApi-maps` (plugin header, most files) vs `TrufiApi-routes` (admin menu pages). Match the file you're editing; don't "fix" it silently.
- Distribution is a zip named `TrufiApi-maps` (`README.md` install steps).
