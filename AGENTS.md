# AGENTS.md

WordPress plugin (Trufi Route Pages) with **no build tooling**: no composer, no autoloader, no linter, no CI. Small dependency-free checks live in `tests/` (`node --test tests/search.test.js`; `wp eval-file .../tests/logic.php` inside WordPress; `python3 tests/smoke.py <site-url>` for semantic HTML/SEO/JSON-LD) — run them after touching grouping, search, labels or markup. Changes are also verified in a real WordPress install against a Trufi GraphQL endpoint: hit `/wp-sitemap-routes-1.xml` for the sitemap, `/{base}` for the routes index page, or a rendered route page at `/{base}/<name>/<route-code>`.

The repo has a tracked local dev stack: `docker-compose.dev.yml` + `.env.dev.example` (see README.md). It isn't named `docker-compose.yml` because `.gitignore` excludes that exact filename and any `docker`/`.docker` path — a rule kept for ad-hoc local files.

## Bootstrap & adding new code

- Entry point is `trufi-maps.php` (the plugin file). It `require`s every PHP file **in a fixed order**; namespaced classes (`App\...`) are NOT autoloaded.
- New classes/files must be added to the require chain in `trufi-maps.php`, or required at point of use (see `functions/sitemap-provider.php:7`).
- The main file refuses to load below `Requires PHP: 8.1` (guarded by `version_compare`). Code may use typed properties and union types.
- Admin-only files are loaded only when `is_admin()`.

## How route pages work (virtual posts)

- Requests match rewrite rule `^{base}/([^/]+)/([^/]+)/?` in `functions/rewrite-rules.php`, mapping to query vars `trufi_map_name` + `trufi_map_id`. Rules are registered on every `init` but **only flushed when they change** (`trufi_maps_flush_rewrite_rules()`: on settings save, and once per plugin version via the `trufi_rewrite_rules_version` option, since uploading a new zip doesn't fire the activation hook). Don't go back to calling `flush_rewrite_rules()` on every request (upstream did): that's a DB write per page view.
- When the "Base Page for Maps" changes, the previous base path is appended to the `trufi_legacy_base_paths` option (`TRUFI_LEGACY_BASE_PATHS_OPTION`) and `{old base}/{name}/{id}` 301s to the same route under the current base (`trufi_legacy` query var, handled first in `trufi_maps_template_redirect()`) — the mobile app and old shares may still link the old base.
- A route URL whose pattern can't be loaded answers **404** (API OK, no such pattern) or **503 + Retry-After** (API failed) via `trufi_maps_route_not_available()` — never a 200 with an empty page (a "soft 404", which is what production served while its API URL was broken).
- No real post exists. `functions/template-redirect.php` (on `template_redirect`) fabricates a global `$post`, stamps `is_page`/`is_singular` on `$wp_query`, and injects minified template HTML into `$post->post_content`. `the_title` is filtered to the route name.
- `{base}` defaults to `routes` but is derived from the "Base Page for Maps" setting via the shared `trufi_get_base_path()` helper (`functions/functions.php`), used by both the rewrite rule and the sitemap provider — keep any future URL-generation code going through that helper rather than re-deriving the base path, or it'll drift again (it used to: the sitemap called `get_page_uri()` while the rewrite rule called `get_post_field('post_name', ...)`, diverging for non-top-level base pages).
- Route URL slug = `sanitize_title(`longName with `→` replaced by a locale word`)` — see `App/Utility.php::replaceArrowWithWord`. **Every** route URL (sitemap provider, index links/share buttons, canonical, JSON-LD, llms.txt, legacy redirects) is built by `trufi_pattern_url()` / `trufi_route_url()` (`functions.php`), with the trailing slash from `user_trailingslashit()` so links point at the final URL rather than one that 301s. Don't build route URLs anywhere else.
- The base page itself (`GET /{base}`, i.e. the page set as "Base Page for Maps", no route segments) renders a **routes index**: searchable sidebar + map of all lines via `trufi_maps_render_routes_index()` (`functions/template-redirect.php`) + `templates/routes-index-template.html`. It calls `remove_all_filters('the_content')` before injecting; WP's default content filters (wpautop, shortcodes, emoji…) corrupt the embedded JS — keep bypassing them if you touch that function. The virtual route page (`templates/map-template.html`, injected by the same file's route branch) does the same for the same reason: its inline script passes HTML strings (e.g. Leaflet `divIcon`s) that wpautop would mangle.
- The REST endpoint and the page both `rawurldecode` the pattern id captured from the URL segment: the index JS sends it `encodeURIComponent`-encoded (`:` → `%3A`) and WP doesn't decode path segments, so an undecoded id 404s.
- Index route rows are plain `<a href>` links to the detail page (QA flow: list → detail → browser Back). The index no longer previews routes on its own map; its map is an overview + geolocation only. `GET /wp-json/trufi/v1/pattern/{id}` (`functions/rest-api.php`) is kept as a public endpoint (no in-plugin caller now); it shares the `trufi_route_data_{mapId}` transient with the virtual route page and `enqueue-scripts.php`.
- Data access (both pages, the REST endpoint, the sitemap) goes through `trufi_fetch_route_data($mapId)` / `trufi_fetch_index_data()` in `functions/functions.php` — thin wrappers around `TrufiApi` that do the "check transient, else fetch + cache" dance once instead of it being duplicated per call site. Every API call runs inside `trufi_api_call()`, which turns failures (`TrufiApi::query()` throws on non-200) into `null` instead of a fatal error, and only **non-empty** results are cached — a failed fetch must never be cached for the whole TTL. Add any new API call the same way rather than re-inlining the transient check.
- `App\Api\TrufiApi::fetchRoute()`'s GraphQL query includes `stops { name, lat, lon, code }` on top of `route`/`geometry`. `Stop.name` in this feed *is* the street/intersection name (e.g. "Avenida Río Paraguay", or literally "Innominada" when the feed has none) — that's the source for the route detail page's "Paradas" list and the street-name marker tooltips, not a separate field. Don't drop `stops` from the query without checking both call sites (route detail page's stop list, REST endpoint's response) still work without it.
- **Data model (v0.11):** lines are grouped by `route.gtfsId` (fallback `shortName|longName|mode`) in `trufi_group_patterns_by_line()` — never by `shortName` alone, which collides across modes ("M", "A", "R", "16"). A line is `{id, shortName, title, mode, sindicato, patterns[{code,longName,from,to,url}]}`; the display title is the feed `longName` via `trufi_line_title()` (leading generic "Bus " dropped, **never** prepend a vehicle word — the vehicle type is unknown).
- **Sindicato** = `route.agency.name` (real names in the feed; the literal `"default"` on a few patterns is ignored). Names that look like a line ("Linea 103", per `trufi_is_line_like_name()`) are rejected. Only then does `trufi_line_sindicato($route, $sindicatos)` fall back to the external OSM-derived dataset (`trufi_sindicatos_url`, `trufi_fetch_sindicatos_data()`: `byName`, `byRef`, `origins`), which also supplies origin names. Unmatched lines have `sindicato: null` (group "Otras líneas").
- **Origin/destination**: `trufi_pattern_labels($longName, $headsign, $sindicatos, $originFallback, $destFallback)` returns `from`, `to`, `subtitle` ("A hacia B"), `sentence` ("Parte desde A hacia el destino B") and `variant`. Origin = dataset `origins`, else the first stop / the "from" part of the OTP `pattern.name`; destination = `pattern.headsign` **unless** it is a vehicle marking ("Panter naranja", "Bandera roja: Nro. blanco" — `trufi_is_vehicle_marker()`), in which case the headsign becomes `variant` and the destination comes from the last stop / the "to" part of `pattern.name` (`trufi_pattern_endpoints_from_name()`, "Innominada" ignored). Both the page and `enqueue-scripts.php` must pass the same fallbacks. Copy never uses an arrow; the route page shows "hacia" in pink (`.trufi-hacia`) and the variant as "Variante del recorrido: …". `longName` is just the line name, don't parse origin/destination from it.
- **Row labels**: `trufi_label_line_patterns()` sets `pattern.label` once per line so no two routes of a line read the same ("Hacia X (Panter naranja)", else "(variante N)"). Server list, `llms.txt`, JSON-LD and `patternLabel()` in JS all read that field.
- Copy rule for all user-facing and AI-facing text: the service helps find registered lines, their sindicato and the route between points; it must **not** imply 24/7 service or published schedules.

## Templates & rendering

- `templates/map-template.html` and `templates/routes-index-template.html` are now **plain static HTML shells** with only text-content `{{placeholder}}` tokens (headline, stats, image/URL attributes — all in ordinary HTML text/attribute positions). There is no inline `<style>`/`<script>` in either file anymore, and no token is spliced into raw CSS/JS syntax positions. This was a deliberate change from the old "splice raw JSON into an inline `<script>` block" approach: besides being a code-editor false-positive magnet (`{{token}}` isn't valid CSS/JS on its own), embedding `json_encode($routeData)` unescaped inside a `<script>` block was a real `</script>`-breakout XSS vector for any route/stop name containing that sequence — GTFS data comes from an external API we don't control. All structured data now travels through `wp_localize_script` (see below), which is run through `trufi_defang_script_close()` first as defense in depth.
- CSS/JS for both pages lives in `assets/css/` and `assets/js/`, loaded via `functions/enqueue-scripts.php` (hooked on `wp_enqueue_scripts`, gated to the two page types this plugin renders); asset `?ver=` is the plugin version plus `trufi-index.js` mtime so browsers pick up edits without a version bump — see "Frontend assets" below. Leaflet 1.7.1 itself stays a raw `<script src>`/`<link>` from unpkg, echoed by `trufi_add_header_tags()` (`functions/functions.php`, on `wp_head` priority 7) rather than a WP-enqueued asset — it isn't re-registered as a WP dependency (that would load it twice); ordering is guaranteed because it prints in `wp_head` before any of our footer-loaded module scripts run.
- Both maps create maps with `zoomControl: false` and re-add the zoom at `bottomright`, restyle `.leaflet-control-zoom` (dark/pink theme) via the shared `.trufi-map` class, and cap `.leaflet-top/.leaflet-bottom` z-index at 400 while the map container gets `z-index: 0; isolation: isolate`. This is load-bearing: the OnePress header is `z-index: 1000`, and without isolation the Leaflet controls (also 1000) escape the map and stack above the sticky header. If you move these styles, keep the isolation.
- The index's search UI is `.trufi-searchbar` (`role="search"`, visible labels): inside `.trufi-index-main` (right column), stacked **above** the map and independent from it; its labels are visually hidden (`.trufi-sr-only`). The `.trufi-map-hint` pill is emptied via `textContent` (no display toggling) and hidden by `:empty` so no blank blob shows. `.trufi-index-body` (sidebar+map row) gets a generous **bounded** height (`80vh`, capped at `860px`) rather than the page itself being height-locked. **Don't go back to `height: calc(100dvh - 82px)` on `.trufi-index`/the whole page** — that was tried and reverted: the theme's `#primary` padding (40px top+bottom) plus the footer mean the page is always taller than one viewport regardless, so it never actually achieved "no scroll"; it just made the `dvh` unit recalculate against a page that scrolls anyway, which read as the footer jumping/"sticky" during scroll on mobile (browser chrome show/hide changes `dvh`). Bounding just the sidebar+map row avoids that. The route detail page (`assets/css/trufi-route.css`) uses the same bounded-height pattern (`.trufi-route-body`/`.trufi-route-map-wrap` at `70vh`) and never had this problem. **On mobile (`<=780px`, `assets/css/trufi-index.css`)** the index becomes a normal stacked scrolling page: `.trufi-index-body` switches to an auto-height column flex layout, the searchbar stays a full-width bar, the map gets a fixed ~320px height, and `order` flips the visual order to hero → search/map → routes list (DOM order is left unchanged: list, then map-wrap). The route detail page follows the same map-first mobile stacking pattern. Accessibility (WCAG 2.2 AA) is part of the contract: the skip link is hidden with a clip until keyboard focus and then `position: fixed` (an absolute one used to land over the theme header); one `<h1>` per page (`trufi_demote_theme_page_title()` turns the theme's title into a `<div>`), no skipped heading levels, skip links, labelled/focusable scroll regions, `aria-live` status, stops as `<button>`s in an `<ol>` — `tests/smoke.py` checks these. Two mobile rules that were bugs before: (1) the searchbar card above the map must stay **positioned** (`position: relative; z-index: 1`) with the map in normal flow (`position: relative; height: 320px`) — a `static` card under an absolutely positioned map is painted beneath it and disappears; (2) never leave a list at the desktop `flex: 1 1 0; min-height: 0` inside the auto-height mobile column — it collapses to 0px and its rows overflow under the theme footer (`.trufi-index-list`, `.trufi-stops-list`). On desktop the searchbar wraps (`flex-wrap: wrap`) rather than squeezing the search input — `nowrap` once shrank it to ~0px, hiding the typed text.
- Route markers follow one convention everywhere (`Trufi.routeDraw.drawEndpoints`, `assets/js/trufi-route-draw.js`): **origin = small solid green dot, destination = red map-pin icon** (`Trufi.icons.pinMarkerSvg()`, a filled teardrop+white-dot SVG rendered via an `L.divIcon` — not a `circleMarker`, and its wrapper needs `.trufi-pin-wrap { background: transparent; border: none; }` in `trufi-shared.css` or Leaflet's default `.leaflet-div-icon` box/border shows through). Intermediate stops are small white-filled rings in the line color (`drawStops`, so they don't hide the line) and clickable from the stop list. The polyline + direction arrows use the admin-configurable `trufi_line_color` option (currently cyan, `#00BCD4`) — that option is the single source of truth for the route's drawn color; don't hardcode a different color for it in CSS/JS.
- Both maps have a geolocation "Mi ubicación" button (browser Geolocation API + `map.locate`, needs HTTPS on production; draws a pulsing marker + accuracy circle), implemented once in `assets/js/trufi-geo.js` (`Trufi.geo.attach(map, {button, onHint})`) and used by both `trufi-index.js` and `trufi-route.js` — don't re-duplicate this block if you touch it, fix it in the shared module. It can be turned off from the plugin Settings: the `trufi_show_location` option drives a `data-show-location="1"/"0"` attribute on the button (CSS hides it on `"0"`, see `trufi-shared.css`), and `Trufi.geo.attach` no-ops its button wiring when the element is missing. On GPS failure/absence it falls back to an approximate IP-based location via client-side `fetch('https://ipwho.is/')` (free, CORS `*`, no key; city/ISP-level precision, drawn as a ~3 km dashed circle + "Ubicación aproximada por IP" hint). Note: in the dev stack the IP lookup resolves the machine's egress IP (a datacenter), not the browser's local network — a false reading in local test.
- QA also tests under a default block theme (Twenty Twenty-Four-style header/footer), so don't rely on OnePress-only markup for layout fixes. The OnePress theme renders its own `<h1 class="entry-title">` page-title banner (wrapped in `.page-header`) above `the_content` on every page, including both of this plugin's virtual pages — there's no filter to suppress just this from the plugin side without a child theme, so `trufi-shared.css` just hides `.page-header` outright. That rule only ever loads on these two page types (gated by `enqueue-scripts.php`), so it's effectively scoped despite `.page-header` being theme markup, not ours.

## Frontend assets (CSS/JS modules)

`functions/enqueue-scripts.php` is the single place that decides which of the two page types is being rendered (checking the same query vars as `template_redirect.php`, since the two hooks don't share state) and enqueues accordingly. All page data (GraphQL results, option values, REST URL, map center/zoom, etc.) is handed to the page's bootstrap script via `wp_localize_script` as `trufiIndexConfig` / `trufiRouteConfig` — don't add new `{{placeholder}}` tokens for anything JS needs; extend the localized config object instead.

- `assets/css/trufi-shared.css` — design tokens (`:root` vars), hero banner, stat blocks, list-title header, line badge, buttons, geo button/pulse marker, stop-list dots, Leaflet chrome theming, `.page-header` hide. Loaded on both pages.
- `assets/css/trufi-index.css` / `assets/css/trufi-route.css` — page-specific layout (including each page's mobile breakpoint), building on the shared classes above.
- `assets/js/trufi-icons.js` — small lucide-style inline SVG icon set (`Trufi.icons`); auto-mounts into any `<span data-icon="name">` on `DOMContentLoaded`, and exposes `Trufi.icons.mount(root)` for icons added dynamically afterward (e.g. list rows built by `trufi-index.js`).
- `assets/js/trufi-geo.js` — the shared "Mi ubicación" button module (`Trufi.geo.attach`), described above.
- `assets/js/trufi-distance.js` — haversine distance helpers (`Trufi.distance`); the route detail page's headline distance stat is computed server-side instead (`trufi_route_distance_km()` in `functions.php`, so it works with JS disabled) — this module is for client-side use, e.g. a future index-page preview.
- `assets/js/trufi-share.js` — `Trufi.share.copyOrShare(url, title)`: native share sheet on touch devices (Web Share API + `pointer: coarse`), otherwise copy (Clipboard API, `execCommand` fallback on plain HTTP) + `Trufi.share.toast()` telling the user the link was copied and to paste it in WhatsApp/another app (or showing the URL to copy by hand if copying failed). Every share control is a **text** "Compartir" button (`.trufi-share-btn`), never an icon-only button: the route detail page's, each route row's (`pattern.url`) and each sindicato group's (`{indexUrl}?sindicato={slug}`) in the index list.
- `assets/js/trufi-route-draw.js` — draws a pattern on a Leaflet map: polyline, direction arrows, green-dot origin / red-pin destination markers, and one small marker per stop with a tooltip showing its street name (`Trufi.routeDraw.drawPattern`). Used by the route detail page's map — this is the module to touch for anything about how a route is painted.
- `assets/js/trufi-search.js` — pure `Trufi.search.filterLines(lines, {query, mode, sindicato})` (mode/sindicato filters ANDed; the query is accent/case-insensitive and ranks **line names only** — exact, prefix, whole word — and falls back to origin/destination only when no line is named like it; it never matches sindicato names; covered by `tests/search.test.js`), kept separate from DOM/rendering code in `trufi-index.js`. The index mirrors its filters in the URL (`?sindicato=&modo=&q=`, `history.replaceState`) so shared sindicato links open pre-filtered and Back from a route page restores the list. Vehicle words in the query ("micro k", "trufi 106", "minibus 46") are split off by `Trufi.search.parseVehicle()` and narrow by line title; the rest is the line name. The index also stores its current view (`url.search` + sindicato label) in `sessionStorage['trufiIndexView']` — on load too, not only on change — and `trufi-route.js` points `.trufi-route-back` at it ("Volver a {sindicato}"), falling back to a same-page `document.referrer`.
- `assets/js/trufi-index.js` / `assets/js/trufi-route.js` — each page's bootstrap: reads its localized config, builds the map, and wires the above modules together. Keep page-specific DOM/rendering code here; put anything reusable in one of the modules above instead. Each pattern in `trufiIndexConfig.lines[].patterns[]` carries a server-computed `url` field (`trufi_pattern_url()`) - that's what the index list's per-row share button links to, not something built client-side.

## SEO, AI crawlers and structured data

- Both virtual pages call `trufi_setup_page_head()` (`functions.php`) from their render function (it must run before `wp_head`). It removes WordPress's `rel_canonical` — which points every virtual route page at the **base page**, i.e. would mark all route pages as duplicates of it — and prints our own single canonical (the route's `trufi_pattern_url()`; for the index, the bare permalink, never the `?q=/?sindicato=/?modo=` filtered URL), sets the document title (`pre_get_document_title`; the route page's `post_title` is just the line name, so themes don't print "X – Site – Site"), `lang="es"` on both pages, description, Open Graph/Twitter (`og:image` = site icon, overridable with the `trufi_og_image` filter), and the JSON-LD `@graph`. Robots meta is left to core `wp_robots` (one tag).
- JSON-LD: `BreadcrumbList` (`trufi_breadcrumb_jsonld()`) on both pages; `BusTrip` on route pages (`trufi_route_bustrip_jsonld()`: line number/name, origin/destination `BusStop` with coordinates, sindicato as `provider`); `ItemList` of every route on the index.
- The index list is **server-rendered** by `trufi_render_routes_list_html()` (`template-redirect.php`) so crawlers that don't run JS (most AI crawlers) see all ~657 route links; `trufi-index.js` only rebuilds it when the visitor filters. Its markup must stay identical to `renderGroup()`/`renderLine()` in `trufi-index.js` (classes, `data-share-url`/`data-share-title` read by the delegated share handler, group order = accent/case-insensitive name sort, labels via `trufi_pattern_row_label()` ↔ `patternLabel()`).
- `/llms.txt` (`functions/llms-txt.php`, rewrite rule in `rewrite-rules.php`): markdown summary + every route link grouped by sindicato, for AI crawlers. A physical `llms.txt` in the site root would shadow it.
- A `robots_txt` filter (`functions.php`) adds `Allow:` for the plugin's `assets/` and a `Sitemap:` line — only for WordPress's virtual robots.txt; production (trufi.app) has rules like `Disallow: /wp-content/plugins/` that block Google from rendering the pages if it's a physical file, which must then be edited by hand.

## Caching & settings

- Four transient caches exist (all keep the `trufi_route%` prefix so the cache cleanup catches them):
  - Per-route: `trufi_route_data_{mapId}`, read via `trufi_fetch_route_data()` (`functions.php`, used by `template-redirect.php`, `rest-api.php`, and `enqueue-scripts.php`)
  - Routes index list: `trufi_routes_index_list`, read via `trufi_fetch_index_data()` (same file, used by `template-redirect.php` and `enqueue-scripts.php`)
  - Sitemap: `trufi_routes_sitemap_xml` in the sitemap provider
  - Sindicatos lookup maps: `trufi_route_sindicatos`, read via `trufi_fetch_sindicatos_data()` (`functions.php`); a failed download is cached as empty for 1 hour
- TTL comes from the `trufi_cache_ttl` option (hours). The admin "Clear Cache" page (`delete_trufi_transients()` in admin/transient-cache-clear.php) clears via raw `option_name LIKE` SQL and only catches the `trufi_route%` prefix — any newly named transient must keep that prefix or be added to the query.
- All option names are `TRUFI_*_OPTION` constants centralized in `functions/constants.php` — reuse, don't string-literal option names.
- Saving settings flushes rewrite rules, records the previous base path for legacy redirects, and clears transients (`admin/admin-settings.php`).
- The Settings page starts with a **read-only status panel** (`admin/status-checks.php`, `trufi_status_checks()`): PHP version, API, sindicatos dataset, base page, rewrite rules, robots.txt, sitemap, store buttons, page-cache plugins. It exists so a site admin without server access can verify a deploy from wp-admin. Its checks must stay read-only (no option or transient writes). Own-site URLs on localhost (local Docker) are fetched via `127.0.0.1` with the original Host header (`trufi_fetch_own_url()`), since the container can't reach its published port.

## Conventions

- Text domain is inconsistent: `TrufiApi-maps` (plugin header, most files) vs `TrufiApi-routes` (admin menu pages). Match the file you're editing; don't "fix" it silently.
- Distribution is a zip named `TrufiApi-maps` (`README.md` install steps).
